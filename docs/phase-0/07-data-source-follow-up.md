## 已完成的私有保护

本次没有对原库执行SQLite连接、checkpoint、store.get、normalizePets、导入、升级或写操作。

1. 只检查候选数据库/WAL/SHM的存在性和文件元数据，观察未有进程打开候选主库。
2. 对完整候选文件集计算采集前hash，将数据库、WAL、SHM复制到Git外的私有目录，再计算采集后hash；两次一致，复制件也逐文件一致。
3. 保留原始文件集只读。另复制到隔离临时目录，允许SQLite在**临时复制件**上读取WAL和处理自身边文件。
4. 临时复制库integrity_check=ok；使用SQLite backup API生成独立一致性SQLite快照。
5. 一致性快照再以只读连接验证integrity_check=ok。保存私有manifest，包含来源路径、原件/备份hash、采集时间和未验证事项。

私有目录权限700，原始文件集与一致性快照权限400，manifest权限600。未生成可公开fixture，没有把孩子记录读入模型、终端输出或Git。没有搬家长凭证/浏览器cookie，也没有调用新项目的导入接口。

这一结果证明：**已保全一份采集期间未变化且可被SQLite读取的候选文件集，并得到通过结构完整性检查的一致性快照。** 它不证明候选就是日常主库、包含最新学习、字段可全部被新应用识别，或已完成应用层恢复。观察无打开进程也不是永久停写承诺。

## 为什么原库的 WAL 不能忽略

该候选确实存在WAL；仅复制progress.sqlite不能证明包含全部已提交记录。后续正式备份应使用真实运行库的在线backup/一致性逻辑导出，或停写后保全完整文件集；不要使用忽略WAL的immutable连接来制造“可打开的备份”。本次仅在复制件执行backup，避免触发旧项目自动升级或修改边文件。

恢复演练必须分两层：SQLite结构可读，以及同版本应用能显示和继续原有学习。当前只通过第一层，第二层需要确认来源版本与实际主记录，不在未获开发授权时直接启动旧应用并迁移它。

## 英语仍需正确的浏览器来源

WordQuest是localStorage；同一个静态服务下，localhost与127.0.0.1、不同端口、不同浏览器、不同设备都是不同来源。服务器目录和一个启动器进程不能证明其中哪份记录是实际学习主记录。

旧应用已有从记录文件恢复、导入前恢复点和导出功能；`scripts/merge_learning_records.js`目前只支持`--inspect`，内容分叉时退出2，并拒绝自动合并。该工具并没有实现安全的V2多设备合并，不能因为有event日志就承诺现成自动合并。

后续先确认真正使用的设备/origin，再由其原应用导出`.wordquest.json`到私有位置。每份记录分别保全，比较完整性和分叉情况；不自动覆盖另一设备，不复原旧scoreLedger已裁剪的奖励，也不重放全量事件补币。
